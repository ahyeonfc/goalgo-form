## 1. 사용 흐름

### 원칙: 찍은 영상만 넘기면 된다 (2026-11-27 사용자 결정)
미리 과제를 고르거나 찍는 자리를 맞추는 단계는 없다. 아무렇게나 찍은 영상이라도 분석기가 무슨 동작인지, 어느 방향에서 찍었는지를 알아채고 그 조건에서 믿을 수 있는 지표만 낸다.

```
 ① 찍기 ─ 폰 기본 카메라(슬로모션 포함). 여러 동작·여러 번을 한 영상에 이어 찍어도 됨
 ② 넘기기 ─ 갤러리에서 영상 공유 → "골고 폼" (홈 화면에 설치한 웹 앱이 공유를 받음)
            설치 전이면 웹 앱 화면에서 영상 고르기
 ③ 자동 분석 ─ 동작 판별 → 구간·회마다 자르기 → 찍은 방향 판별 → 크기 기준 → 지표 → 점수
 ④ 결과 ─ 동작별 점수, 세 축, 지난번 대비, 고칠 점 2~3개 + 그 장면(관절 선 겹침, 느리게 보기)
          판별이 틀렸으면 동작 이름을 눌러 고침(→ 다시 계산)
 ⑤ 저장 ─ 폰에 바로 저장, 내 드라이브 "골고폼/" 에 백업(결과는 바로, 원본 영상은 와이파이일 때). 8절
```
- 골고 캠(촬영 앱)은 쓰지 않는다. 슬로모션·초광각을 그대로 쓰기 위해서다.
- 같은 날 넘긴 영상은 한 "레슨"(날짜 단위)으로 묶인다. 날짜는 영상 파일의 촬영 시각.
- 찍는 자리 안내는 미리 하지 않고, 결과 화면의 한 줄 조언으로만 준다. 예: "옆에서 찍으면 디딤발 위치도 볼 수 있어요", "120fps 슬로모션으로 찍으면 공 속도도 잴 수 있어요".
- 동작 문서(lesson/*.md)의 "훈련 방식·찍는 자리"는 **이렇게 하면 더 많은 지표를 정확히 낸다**는 권장으로 남긴다(필수 아님).

### 동작 판별 (자동)
| 판별 | 규칙 (첫 판) |
|---|---|
| 달리기·민첩성 | 공이 몸 가까이 없음(또는 화면에 없음) + 몸 속도가 큼 |
| 드리블 | 터치(`touch`)가 1.5초 안 간격으로 3번 넘게 이어짐 + 몸이 움직임 |
| 슈팅 | 임팩트 직전 공이 거의 정지/느림 + 임팩트 뒤 공 속도가 큼(첫 판 15m/s 넘음, 시험으로 맞춤) 또는 공이 뜸 |
| 패스 | 임팩트 뒤 공이 땅으로 감 + 공 속도가 슈팅 기준 아래 |
| 퍼스트 터치 | 굴러오는(또는 날아오는) 공이 몸 1m 안에서 터치 후 크게 느려짐 |
- 한 영상 안에서 구간마다 판별하므로 섞여 있어도 나뉜다. 확신이 낮은 구간은 "무슨 동작인가요?"로 결과 화면에서 묻는다.

### 찍은 방향 판별 (자동)
- 어깨 폭·엉덩이 폭(키 대비)과 이동 방향(화면 가로인지 깊이인지)으로 **옆 / 정면·뒤 / 비스듬** 셋으로 나눈다.
- 지표마다 동작 문서에 적힌 "찍는 각도"와 맞지 않으면 그 지표는 "이 각도에서는 안 보임"으로 비우고 점수에서 뺀다.
- 장면 속도(fps)도 영상 정보에서 읽어, 120fps 가 필요한 지표(공 속도, 임팩트 순간 값)는 30fps 영상에서 뺀다.

### 정해진 코스 알아채기
- 콘 배치가 동작 문서의 과제와 맞으면(예: 콘 6개 일직선 약 2m 간격 → 드리블 슬라럼, 콘 2개 5m 간격 + 왕복 → 505) 그 과제로 보고 **연구 기준값과 비교하는 지표**(슬라럼 손실, 10~20m 구간 속도, 505 시간 등)까지 낸다.
- 코스를 모르면 그 지표는 빼고 나머지는 내 지난 기록과 비교한다.

### 회마다 자르기 (한 영상에 여러 번)
- 판별한 동작의 시작·끝 사건으로 자동으로 자른다.
  - 드리블: 출발(몸이 출발선에서 움직이기 시작) ~ 도착(출발선 넘음). 공 있이/없이는 공이 화면에 따라다니는지로 구분.
  - 슈팅·패스: 임팩트(`impact`)마다 1회. 앞 2초 ~ 뒤 1초.
  - 퍼스트 터치: 공이 받는 사람 1m 안에 들어올 때마다 1회.
  - 달리기: 선 넘는 사건 순서로.
- 자른 결과를 띠로 보여 주고, 틀린 것은 눌러서 지우거나 경계를 옮긴다. 첫 1회는 "연습"으로 자동 표시(동작 문서 규칙).

## 3. 보정 (화면 좌표 → 바닥 좌표)

지표 대부분이 m·cm·키 비율이라 영상마다 크기 기준이 필요하다. **콘이 없어도 된다.** 기본은 공과 키로, 콘이 있으면 더 정확하게.

### 기본 (콘 없음)
- **키**: 선 자세 구간의 머리~발목 길이(px)와 입력한 키(cm)로 사람 있는 자리의 cm/px.
- **공**: 공(지름 22cm)이 보이는 장면마다 공 크기로 그 자리의 cm/px. 카메라에서 멀어지면 작아지므로, 공 크기의 변화로 깊이 방향 위치도 대략 안다.
- 둘이 10% 넘게 다르면 경고(초광각 가장자리, 사람이 공보다 카메라에 훨씬 가까움 등).
- 바닥 평면 변환은 없으므로 깊이 방향 거리·속도는 "참고"로 내린다.

### 콘이 있을 때 (더 정확)
1. **콘 자동 찾기**: 첫 1초 장면들에서 콘(주황·노랑 원뿔, 접시콘)을 색과 모양으로 찾는다. 과제마다 콘 개수와 간격을 알고 있으므로(예: 슬라럼 6개 2m), 찾은 점을 그 배치에 맞춘다.
2. **확인·고치기**: 찾은 콘에 번호를 붙여 보여 주고, 틀린 것은 눌러서 옮긴다. 콘이 4개 이상 바닥에 있으면 바닥 평면 변환(호모그래피)을 만든다. 2~3개뿐이면 일직선 거리 환산만.
3. **공 크기 확인**: 공(지름 22cm)이 정지해 있는 장면에서 공 크기로 그 자리의 cm/px 를 다시 재서 2와 10% 넘게 다르면 경고.
4. **카메라가 움직였나**: 콘 위치가 영상 중간에 3px 넘게 바뀌면(삼각대 흔들림) 경고하고, 바뀐 뒤 구간은 다시 맞춘다.

### 한계
- 몸(발이 들린 순간, 머리 등)은 바닥 위에 있어 바닥 변환을 그대로 쓰면 틀린다. 바닥 변환은 **바닥에 닿은 것(착지한 발, 굴러가는 공, 콘)** 에만 쓰고, 몸 안의 길이(보폭은 착지 발끼리라 됨, 무게 중심 높이 등)는 키 비율로 쓴다.
- 초광각 가장자리는 휜다. 폰 기종별 렌즈 왜곡을 한 번 재 둘 수 있으면 좋지만, 첫 판은 "중요한 장면을 화면 가운데에 두게" 찍는 자리 안내로 피한다.

## 4. 어디서 분석하나 🔶

### 추천: 폰 브라우저 안에서 (첫 판)
- 이유: 레슨 끝나고 바로 본다. 서버·Colab·업로드 대기가 없다. 영상이 폰 밖으로 나가지 않는다. 비용 0.
- 자세: **MediaPipe Pose Landmarker**(웹, 33점, 발뒤꿈치·발끝 포함). 기본은 full 모델, 느리면 lite.
- 공: 경기 분석기용으로 학습한 **YOLO26s 사람+공 감지기의 사본**을 ONNX 로 바꿔 이 프로그램 저장소에 두고 onnxruntime-web(WebGPU, 안 되면 WASM)으로 돌린다(0절). 축구공에 맞춰 학습돼 있어 일반 모델보다 낫다. 실패하면 MediaPipe 물체 감지(COCO "sports ball")로 바꾼다.
- 콘: 색 찾기(모델 없음).

### 두 번 훑기 (속도 대책)
- 120fps 영상은 장면이 30fps 의 4배다. 폰 브라우저 자세 추정은 초당 약 15~30장으로 예상(시험 필요)이라 전부 돌리면 영상 길이의 4~8배가 걸린다.
- 1차: 30fps 간격으로 자세·공을 돌려 사건(임팩트, 터치, 선 넘기)을 대략 찾는다.
- 2차: 사건 앞뒤 0.3초만 원래 장면 수(120fps)로 다시 돌린다.
- 영상 읽기는 `requestVideoFrameCallback` 또는 WebCodecs(`VideoDecoder`)로 장면을 하나씩 꺼낸다. 4K 영상은 1280px 로 줄여서 돌린다(가까이 찍은 한 사람이라 충분).

### 대안: Colab(나중에, 정확도가 부족할 때)
- 더 큰 자세 모델(RTMPose 등)과 전체 장면 분석. 영상을 드라이브에 올려야 해서 기다림·데이터가 든다.
- 같은 계산 엔진(5절)을 Python 으로도 두면 브라우저 결과와 비교 시험에 쓸 수 있다.

### 먼저 할 시험
- S25·폴드3 브라우저에서 1080p 30fps·120fps 영상 10초를 MediaPipe full/lite 로 돌린 속도.
- 같은 영상에서 공 찾기 성공률(우리 감지기 대 MediaPipe 물체 감지).

## 5. 공통 계산 엔진 (①·②)

모든 동작이 같은 엔진을 쓴다. 동작별 차이는 기준표 파일(6절 형식)로만 준다.

### 5.1 장면별 원재료
장면마다 `{t, kp:[33×(x,y,vis)], ball:{x,y,r,conf}|null, cones?}` (화면 좌표, 1280px 기준).

### 5.2 손질
| 단계 | 규칙 |
|---|---|
| 신뢰도 거르기 | 관절 `vis` < 0.5 이면 그 관절은 빈칸 |
| 짧은 빈칸 채우기 | 빈칸이 0.1초 이하면 앞뒤로 선형 보간. 더 길면 빈칸 유지(지어 채우지 않음) |
| 흔들림 줄이기 | 위치는 One Euro 필터(느릴 땐 강하게, 빠를 땐 약하게). 사건 순간 값(임팩트 무릎 등)은 필터 전 값과 필터 후 값을 둘 다 남기고, 차이가 크면 믿음도를 내린다 |
| 좌우 뒤바뀜 | 왼·오른 다리가 한 장면만 바뀌어 튀면(옆에서 찍을 때 흔함) 앞뒤 장면과 이어지는 쪽으로 바로잡는다 |
| 공 끊김 | 공이 0.2초 안 끊기면 직선 보간, 더 길면 빈칸 |
| 키 | 선 자세(속도 거의 0인 구간)의 머리~발목 길이로 화면 속 키(px)를 잡고, 입력한 키(cm)와 맞춰 cm/px 를 하나 더 얻는다(3절 확인용) |

### 5.3 기본 측정값 (①)
[lesson-criteria.md](lesson-criteria.md) ① 표의 값을 장면마다 계산한다. 각도는 화면 평면 각도, 길이는 키 비율과(바닥에 닿은 것만) m.

### 5.4 사건 찾기 (②)
| 사건 | 규칙 (첫 판) |
|---|---|
| 착지 `step` | 발끝·발뒤꿈치 높이가 그 발의 최저 높이 + 키의 2% 안이고, 발 속도가 키의 1.5배/초 미만인 구간의 시작 |
| 터치 `touch` | 공과 가까운 발끝 거리가 키의 10% 안으로 들어온 구간에서 가장 가까운 장면, 그리고 직후 공 속도 크기나 방향이 15% 이상/20° 이상 바뀜. 앞 터치와 0.25초 이상(드리블 연구 정의) |
| 디딤 `plant` | 임팩트 전 마지막 반대발 착지 |
| 임팩트 `impact` | 차는 발과 공 거리가 최소인 장면이면서 직후 공 속도가 직전보다 2배 이상(정지 공이면 0 → 움직임) |
| 방향 전환 `cut` | 몸 이동 방향(엉덩이 중심, 0.2초 평균)이 45° 이상 바뀐 구간의 가운데 |
| 선 넘기 | 엉덩이 중심이 보정한 선(콘 두 개를 잇는 선)을 넘는 장면. 장면 사이는 직선 보간으로 시각을 나눈다(120fps 면 약 4ms 단위) |

- 규칙의 숫자(키의 10% 등)는 시험(7절)으로 맞춘다. 모두 기준표 파일의 "엔진 설정"에 둔다.

## 6. 기준표 파일 형식

문서(lesson/*.md)와 코드가 같은 내용을 보도록 동작마다 JSON 하나. 위치: 이 프로그램 저장소의 `criteria/{동작}.json`(웹 앱이 읽음). 문서를 고치면 이 파일도 같이 고친다.

```json
{
  "id": "dribble", "ver": "2026-11-27",
  "tasks": [
    {"id": "A", "name": "슬라럼 왕복", "cones": [{"n":6,"gap":2.0,"first":1.0}],
     "fps_min": 30, "cam": {"pos": "출발선 뒤 3m", "h": 1.5, "img": "dribble_A.svg"},
     "reps": {"ball": 2, "noball": 1}, "warmup": 0}
  ],
  "phases": [{"id":"start","from":"move","to":"cone1"}, {"id":"cones_out","from":"cone1","to":"coneN"}],
  "metrics": [
    {"id":"drb.loss","name":"드리블 손실","axis":"speed","unit":"s",
     "calc":{"op":"sub","a":"drb.time@ball","b":"drb.time@noball"},
     "trust":"high","ref":"R2","score":{"lo":0,"hi":4.06,"t":1.06},
     "note":"유소년 14세 평균 기준",
     "fix":{"above":"공 없이 달릴 때보다 많이 느립니다. 콘 구간에서 터치를 작게…"}}
  ],
  "refs": {"R2": {"text":"슬라럼 왕복 손실 U14 4.06±0.53초","src":"Milanović 2025","url":"…"}},
  "engine": {"touch_dist": 0.10, "touch_gap": 0.25, "cut_deg": 45}
}
```
- `score` 가 없는 지표는 "개인 비교"(첫 3회 평균이 기준선).
- `trust`: high(1배) / mid(0.5배) / ref(점수 제외).
- `calc` 는 엔진이 아는 계산 몇 가지(순간값, 구간 평균·최대·P90, 비율, 차, 횟수)의 조합으로만 쓴다. 새 계산이 필요하면 엔진에 추가.

## 7. 정답 만들기 도구와 시험

정확도를 확인하려면 사람이 표시한 정답이 필요하다.

### 표시 도구 (이 웹 앱 안, "시험" 화면)
- 영상을 한 장씩 넘기며 사건(터치, 임팩트, 디딤, 착지, 선 넘기) 순간에 버튼을 누른다.
- 필요한 장면에서 관절 두세 개(무릎, 발목, 공 중심)를 눌러 위치를 표시한다(각도 정답용).
- 결과는 `{영상 id, 사건:[{type, t}], 점:[{t, name, x, y}]}` 로 저장.

### 시험 항목 (동작 문서 "시험"을 모은 것)
| 무엇 | 비교 | 목표 |
|---|---|---|
| 사건 시각 | 자동 대 사람 표시 | ±2장면 안 90% 이상 |
| 선 넘기 시간 | 자동 대 사람 표시 | ±0.02초(120fps) |
| 무릎·몸통 각도 | 자동 대 사람이 그은 선 | ±4~5° 안 |
| 공 속도 | 자동 대 사람이 찍은 공 위치로 계산 | ±1.5m/s |
| 지표가 갈리나 | 잘한 시도 대 일부러 틀린 시도 | 점수 차가 뚜렷 |

- 결과는 분석기의 IDF1 시험처럼 차수로 기록한다(`docs/lesson-tests.md`, 첫 시험 때 만듦).

## 8. 저장

**분석은 폰 안에서, 기록과 원본 영상은 내 구글 드라이브의 별도 폴더에 백업**(2026-11-27 사용자 결정). 골고 경기 영상(`MatchCam/`)과 섞지 않는다. 서버 데이터베이스는 쓰지 않는다.

### 폴더 구조 (드라이브)
```
골고폼/                         ← 골고의 MatchCam/ 과 따로
  profile.json                    키·주발·설정
  2026-12-02/                     레슨(촬영 날짜) 단위
    lesson.json                   그날 영상 목록, 메모, 결과 요약
    v_143055/                     영상 하나(촬영 시각 HHmmss)
      original.mp4                원본 영상(백업)
      result.json                 동작 구간·회마다 지표·점수·찍은 방향·fps·엔진/기준표 버전
      raw.json.gz                 손질 전 장면별 관절·공·콘 좌표(다시 계산용)
      truth.json                  사람이 표시한 정답(있을 때만)
  coach/                          코치 시범(같은 구조)
```

### 흐름
1. 분석이 끝나면 `result.json`·`raw.json.gz` 를 먼저 폰(브라우저 저장소 IndexedDB)에 저장 → 결과를 바로 보여 줌.
2. 로그인돼 있으면 결과 파일을 바로 드라이브에 올린다(작음).
3. **원본 영상은 와이파이일 때만** 백업한다(120fps 1분 약 400MB). 모바일 데이터면 "와이파이에서 올리기" 대기열에 넣고, 앱을 다음에 열었을 때 와이파이면 이어서 올린다(이어 올리기 지원).
4. 원본이 드라이브에 다 올라가고 크기가 맞으면 "폰에서 지워도 됨" 표시. 폰 영상을 앱이 지우지는 않는다(갤러리 영상은 사용자 것).
5. 다른 기기(PC 등)에서 열면 드라이브의 기록을 읽어 같은 결과·장면을 본다.

### 왜 이렇게
- 원재료(`raw`)가 있으면 기준이 바뀌어도 영상 없이 다시 계산한다.
- 원본이 드라이브에 있으면 더 좋은 자세 모델로 다시 분석할 수 있고, 폰에서 지워도 장면 보기가 된다.
- 드라이브 권한은 drive.file(이 프로그램이 만든 파일만). 다른 드라이브 파일은 못 본다.
- 원본은 기한 없이 보관한다. 지울 때는 사용자에게 먼저 묻는다(골고 원본과 같은 원칙).

### 구글 등록 (한 번)
- 새 Google Cloud 프로젝트, OAuth 동의 화면 "프로덕션"(drive.file 은 비민감 범위라 검증 불필요), **웹 애플리케이션** OAuth 클라이언트(승인된 출처 = 이 웹 앱 주소). 브라우저는 Google Identity Services 로 로그인.
- 설정 안내 문서는 저장소를 만들 때 함께 쓴다(폰 기준).
